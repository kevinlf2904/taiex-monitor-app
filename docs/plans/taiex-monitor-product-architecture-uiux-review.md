# 第二輪技術審查：產品架構、UI／UX 與功能升級規劃

> 審查對象：`docs/plans/taiex-monitor-product-architecture-uiux-plan.md`（PR #156）
> 依據：main `7145b04`，網站版本 `2026.10.24-158`
> 審查者：Claude Code，2026-10-25（台北）
> 本輪只做審查與寫文件，沒有修改任何應用程式程式碼。

---

## 0. 結論摘要

規劃的大方向可以保留：四大主導覽不變、今日市場加盤中監控兩個入口、先做頁面開著時的前端監控再做伺服器監控、沿用現有元件。

但核對程式碼後，有 **8 個必須修正的錯誤或遺漏**。其中 4 個會直接造成功能錯誤或資料風險：

1. M1 監控的報價覆蓋範圍；
2. 休市日的時段判斷；
3. 新分頁與使用者已存的分頁順序；
4. 事件資料被雲端同步帶走。

另外 M2 的首選排程方案和多處設計可以再簡化。

修訂後最大的順序調整：

- **把「接上 Upstash＋Telegram」提前成第 0 步。** 這一步不用寫程式，而且能立刻修好目前送不出去的早報和收盤推播。
- **把「休市日判斷」從共用基礎裡拉出來先做。** 它影響目前線上每個使用者。

## 3. 建議刪除或簡化的設計

| # | 原設計 | 簡化成 | 理由 |
|---|---|---|---|
| S1 | 事件生命週期 5 狀態（OPEN、UPDATED、CLOSED、DATA_INSUFFICIENT、DISMISSED）＋盤後結論 | **`state: open｜closed`＋`level`（分桶）＋`verdict`**。「已更新」只是 `lastAt` 與 `level` 改變；資料不足時**不產生事件**，改記在健康度；「不用理」是本機的 `muted` 旗標 | 沒有人工處理流程，多的狀態只增加測試量 |
| S2 | 資料狀態 7 種（LIVE、DELAYED、STALE、PARTIAL、CLOSED、ERROR、LOADING） | 畫面上的新鮮度標籤只要 **4 種：即時、延遲、過期、休市**。載入中與錯誤沿用現有骨架屏與「原因＋重試」；資料不完整是**卡片層級**的「資料暫缺」（現有），不是頁面狀態 | 現有元件已涵蓋 3 種；標籤越少越好懂 |
| S3 | 時間欄位 5 個 | 只用 **`sourceAt`（來源時間）、`at`（取得時間）、每個來源的 `okAt`（最後成功時間）** | `published_at` 只有新聞用、`processed_at` 沒有用途 |
| S4 | 「明日觀察清單」新建一份可勾選清單 | **沿用現有的「筆記追蹤」**（`brief.js:1729`，`watch:notes`）：盤後面板每檔給「加入追蹤」按鈕，寫入筆記並可設目標價（就是現有到價提醒） | 已有清單、筆記、到價提醒、雲端同步；新建一份就是重複功能 |
| S5 | 時段面板的選擇記住到當天 | **不記**，每次進來都跳到目前時段 | 少一個狀態、少一組測試；使用者要看別的時段點一下就好 |
| S6 | M1 事件類型 9 種 | M1 先做 **5 種**：大盤漲跌跨門檻、自選與庫存漲跌與漲跌停、今日市場關鍵價位、使用者既有的到價與指標提醒、資料異常。族群輪動、量能異常、期現貨背離、新聞延到 M2 之後 | 這 4 種都需要新的歷史資料（同時段量、排名快照）或新邏輯 |
| S7 | 誤報統計 | 延後，先只在歷史頁列出 `verdict` | 事件量不夠時統計沒有意義 |
| S8 | M2 首選 QStash | **首選改成 GitHub Actions**（見 6.2 的比較）；QStash 當升級選項 | 不用新服務、不用新的公開 API、沒有簽章驗證要寫；和現有 `alerts-push`、`morning-brief` 同一種寫法 |
| S9 | 手機核心卡「兩欄＋橫向捲動」 | 擇一：**兩欄網格**，缺資料的卡縮成一行 | 原寫法兩種模式互相矛盾；兩欄網格較少誤觸 |
| S10 | 事件詳情網址 `#monitor/<完整 ID>` | `#monitor/<8 碼短雜湊>` | 完整 ID 含冒號、日期，網址長又醜；`applyRoute` 以 `/` 切段，短雜湊最安全 |

## 4. 修訂後的實作順序與依賴

```
P0 接上 Upstash＋Telegram（使用者設定，不寫程式）
P1 休市日判斷修正（小 PR，影響所有現有使用者）
P2 決策中心整理（樣式、資金卡去重、休市推演、標題、同步排除）
P3 今日市場改版（改名、三層、時段面板、加入追蹤）
P4 盤中監控 M1（前端）
P5 盤中監控 M2（伺服器：GitHub Actions＋KV＋Telegram）   ← 依賴 P0、P4
P6 盤後驗證、歷史頁、跨模組連結                          ← 依賴 P4（M2 有更好）
```

- P1、P2 互相獨立，可以並行。
- P3 依賴 P2：同一批檔案，先整理再改版，避免衝突。
- P4 依賴 P1（休市判斷）和 P2（同步排除）。
- P0 不擋 P1–P4，但 P5 一定要有它。

**和原規劃的差異**
- 新增 P0、P1。
- 原 Phase B 拆成 P1、P2，而且不再包含「統一時段函式」這種大重構，只修會造成錯誤的地方。
- M2 改用 GitHub Actions。
- 原 Phase F 併入 P6。

| 失效處理 | API 失敗就記一筆 run 失敗、不產生事件；連續 3 次失敗在監控頁標示「伺服器巡檢中斷」；Telegram 失敗寫入事件的 `notified[].err` |
| 測試 | `scripts/monitor.mjs --dry`（不需要 KV）；單元測試 KV 用記憶體替身驗證冪等；workflow 先用 `workflow_dispatch` 加 `dry=1` 跑 |
| 回滾 | 在 GitHub 停用 workflow（一鍵），或刪 workflow 檔；前端偵測不到伺服器資料就自動回到 M1 |

### P6：盤後驗證、歷史、跨模組

| 項目 | 內容 |
|---|---|
| 檔案 | `learner/monitor.js`（`monVerify`）、`scripts/monitor.mjs`（在 `market-scan` 之後跑一次驗證）、監控歷史頁、今日市場盤後面板的事件驗證摘要、個股頁的「今天的事件」、今日重點卡的事件數 |
| 測試 | 驗證三種結論；歷史依日期讀取；每個跨頁連結都有返回路徑 |
| 回滾 | revert；資料都有過期時間 |

**所有階段的共同要求**：照 AGENTS.md，改 `watch.html`、`index.html` 先開「鎖：」draft PR；合併前改版本號與 README；CI 綠、Antigravity 驗證、ChatGPT 稽核。

### 6.1 要不要先接上 Upstash＋Telegram（P0）

| 選項 | 頻率與延遲 | 成本 | 風險、維運 |

| B. Upstash QStash | 每 1–2 分鐘，準時 | 免費額度以官網為準；盤中每 2 分鐘約 135 則／天 | 要申請簽章金鑰、寫簽章驗證；多一支公開 API（`/api/monitor`）要防濫用 |
